# YOLO Pose Web：延时优化与网球测速 / 模型精调方案

本文基于当前实现（`app.js`、`lib/ball_tracker.js`、`export_tennis_onnx.py`、Nginx `/yolo-pose/`）的代码级结论，回答两件事：

1. 实时链路慢在哪、怎样把端到端延时压下来。
2. 现有「估速」能不能当产品能力用，以及检测模型要怎么优化 / 用什么数据精调。

推理全部发生在**打开页面的设备浏览器**里；云主机只发静态文件，不决定帧耗时。

---

## 1. 现状架构（与延时相关的部分）

```
getUserMedia 1280×720 ≤30fps
        │
        ▼  drawImage → sourceCanvas（原分辨率）
        │
        ▼  letterbox 640×640 + getImageData + JS 转 NCHW Float32
        │
        ├─► session.run(yolo11n-pose.onnx)          串行
        └─► tennisSession.run(yolo11n-tennis.onnx)  串行（网球开时）
                    │ 仅取 COCO class 32 = sports ball
                    ▼
              pickPrimaryBall（最高分，不是最近轨迹）
                    ▼
              BallTracker：最近邻 + EMA + 球直径 6.7cm → km/h
                    ▼
              主线程 Canvas 画骨架 / 黄框 / 轨迹 / HUD
```

| 项 | 实现事实 |
| --- | --- |
| 姿态 | `models/yolo11n-pose.onnx`，输出 `[1,56,N]`，imgsz=640 |
| 网球 | `models/yolo11n-tennis.onnx`（仓库内约 11MB），由 **COCO 预训练 yolo11n.pt 直接导出**，**不是**单类网球微调模型 |
| 解码 | `decodeDetectSportsBall` 硬编码 `SPORTS_BALL_CLS = 32`；单类模型导出后这段必须改 |
| 兜底 | ONNX 失败则整图 HSV 黄绿连通域（`detectTennisHsv`） |
| 后端 | 优先 WebGPU（`ort.webgpu.min.js` @1.20.1），失败 WASM；多线程仅 `crossOriginIsolated` |
| 帧率帽 | `maxFps=30`，但 `inferBusy` 会丢中间帧，**实际 FPS ≈ 1000/整帧 ms** |
| 摄像头 | `facingMode: user`（自拍），球场侧拍更合理的是 `environment` |
| 测试图 | `assets/bus.jpg` 有；`tennis-sample.jpg` **未入库** |

README 实测（iPhone Safari、同一测试图）：CPU 双模约 505ms（~2 FPS）；WebGPU 约 244ms（~4 FPS）。这与「目标 ≥10 FPS」仍差一截。

当前公网路径是 Nginx `proxy_pass` 到 `127.0.0.1:8765`，示例里的 COOP/COEP **未必生效**，WASM 多线程经常用不上。WebGPU 成功时这一点次要。

## 2. 延时拆解：时间花在哪

整帧时间 ≈ **预处理 + 姿态推理 + 网球推理 + 后处理绘制**。WebGPU 下后两者占绝对大头，且**相加**而不是取 max。

### 2.1 已证实的大头

| 环节 | 量级（WebGPU / iPhone） | 说明 |
| --- | --- | --- |
| 姿态 `session.run` | ~136 ms | 640 全图，每帧必跑 |
| 网球 `tennisSession.run` | ~87 ms | 同样 640 全图，与姿态**串行** |
| letterbox + `getImageData` + JS NCHW | 常十余 ms 级 | 409600 像素 ×3 的 JS 循环；`willReadFrequently` 已开，缓冲已复用 |
| 解码 + NMS + Canvas | 几 ms | 相对推理可忽略 |
| HSV 兜底 | 可达数十～上百 ms | 原分辨率双重像素扫描 + 连通域，**比 ONNX 更不适实时** |

摄像头 cap 30 FPS **不是瓶颈**：推理 244ms 时，`loop` 里 `inferBusy` 直接跳过后续 rAF，显示落后真实世界约 **一整帧推理时间**（~0.25s）。测速用的 `performance.now()` 间隔也是这个墙钟，不是视频时间戳。

### 2.2 结构性问题（比「再挤一点 JS」更重要）

1. **双 640 模型串行**：理论下限 ≈ pose + tennis；并行后下限 ≈ max(pose, tennis)。
2. **网球用全图 80 类检测**：算力浪费在 79 个无关类；小球像素占比极低，640 仍吃力，320 全图又更易漏。
3. **预处理在 CPU**：GPU 推理前后各一次 CPU↔GPU 同步；NCHW 转换未上 WebGL/WebGPU。
4. **采集分辨率偏高**：1280×720 只为再缩到 640，增加 `drawImage` 与内存带宽。
5. **主线程推理**：即使 FPS 不变，UI 也会跟着卡；ORT `wasm.proxy` / Worker 可把卡顿和「感觉延时」分开。
6. **显示滞后 = 推理时长**：没有「采集时间戳 → 结果对齐」的流水线，HUD 永远是上一拍算完才画。

## 3. 提高响应速度的方案（按优先级）

原则：**先减重复计算与串行等待，再考虑降分辨率 / 量化。** 测速需要稳定的球心序列，盲目隔帧或 320 全图会先把轨迹打死。

### P0 — 工程，不改权重（**已落地** 2026-09-17）

| 项 | 做法 | 状态 |
| --- | --- | --- |
| **网球 ROI** | `lib/yolo_infer.js`：miss&lt;2 时原图裁 256–384，letterbox 320；否则全图 640 | 已实现；`?roi=0` 关闭 |
| **姿态 / 网球并行** | 同一 Worker 内 `Promise.all` 两个 `session.run` | 已实现 |
| **推理移出主线程** | `lib/infer.worker.js`；失败回退主线程 | 已实现；`?worker=0` 关闭 |
| **摄像头** | 默认后置、宽 960；「镜头」切前置 | 已实现；`?facing=user` |
| **COOP/COEP** | Nginx 反代 8765（`/root` 不可 alias）+ location 内 `always` 隔离头 | 已上 `api.uchance.tech` |
| **本地 ORT** | `download_ort.py` → `lib/ort/`（1.20.1，含 jsep.wasm） | 已下载到本机；不进 git |

复测：HUD 应出现 `[worker]`；网球跟上后出现 `网球ROI`。真机 WebGPU 整帧目标从 ~244ms 降到接近姿态单路。

### P1 — 以可接受精度换速度

| 项 | 适用 | 不要用在 |
| --- | --- | --- |
| 网球 `imgsz=320/416` **仅 ROI 内** | ROI 已锁定后 | 远场全图（漏检会毁掉测速） |
| 网球隔帧（2 pose : 1 tennis） | 只看骨架、估速关闭 | 打开估速时（4 FPS 再减半，轨迹更稀） |
| FP16 导出 | WebGPU 设备 | 老 WASM 路径需测算子覆盖 |
| INT8 | 桌面校准集充分后 | 小目标网球，易掉召回 |
| 更小骨干 `yolo11n` → 已是 n；可试 `yolo11n` 单类（通道更少）比换 `yolov8n` 更划算 | 单类微调后 | 继续 80 类 COCO 代理 |

Query 已支持 `?imgsz=320`，但姿态与网球共用一个 `cfg.imgsz`。优化时应拆成 `poseImgsz` / `tennisImgsz`。

### P2 — 预处理 GPU 化（中期）

`getImageData` 强制像素读回，是 WebGPU 路径上不该存在的同步点。用 OffscreenCanvas / WebGL 着色器做 letterbox + `/255` + NCHW（或改用 ORT 接受 NHWC 的预处理图，若版本支持）可再省一轮 CPU。优先级低于 ROI + 并行。

### 目标帧率怎么定

| 场景 | 建议目标 | 含义 |
| --- | --- | --- |
| 只开姿态 | ≥12–15 FPS | 骨架可跟挥拍 |
| 姿态 + 网球框（不测速） | ≥10 FPS | 观感可接受 |
| 姿态 + 测速 | **稳定 15+ FPS 检测**，或 30fps 视频离线 | 见第 4 节：4 FPS 不够支撑球速物理 |

业余发球约 30–45 m/s，业余底线抽球常见 20–35 m/s。4 FPS 时球在图上可跳几十～上百像素，超过 `matchPx=90` 的关联阈值，轨迹会被当成「新球」重置，速度归零。**不先把检出频率做上去，精调检测模型也救不了测速。**

## 4. 网球测速功能是否可用

### 4.1 结论（分级）

| 级别 | 判定 | 说明 |
| --- | --- | --- |
| Demo / 教学 HUD | **可用** | 球被持续框住时，轨迹方向和「快/慢」量级能对上观感 |
| 训练辅助（给学员一个数） | **不可靠** | 误差常达数倍，且随机位、模糊、漏检跳变 |
| 赛事 / 对比上次击球 | **不可用** | 无 3D、无球场标定、采样过稀，不能当量化指标 |

产品文案保持现状即可：「估计球速 / 飞行距离（平面近似）」。不要对标雷达枪或鹰眼。

### 4.2 算法在算什么

`lib/ball_tracker.js`：

- 尺度 \( s = 0.067 / d_{\mathrm{px}} \)，\( d_{\mathrm{px}} \) 为框宽高均值（最小 4px）。
- 相邻检出中心像素位移 × \( s \) / \(\Delta t\)，再 EMA（α=0.55）得到 km/h。
- \(\Delta t\) 来自 `performance.now()`（推理完成时刻），不是 `video.currentTime`。
- 关联：欧氏距离；阈值 `max(90px, 2.5·速度对应位移)`；过大则 **整条轨迹重置**。
- 无卡尔曼、无击球分段、无多目标（`pickPrimaryBall` 只取最高分）。

这是公路测速那套「检测 → 跟踪 → 像素/米」的简化版，标定物选了**球直径**而不是车道线。

### 4.3 系统误差（即使检测完美也会错）

1. **单目平面速度 ≠ 3D 球速**  
   只测成像平面投影。球沿光轴飞（来球正对镜头）时投影速度接近 0；斜穿画面时被放大。专业测速要球场单应 / 多机 / 雷达。

2. **直径标定在远距和运动模糊下崩**  
   远距框 6–10px，1px 误差就是 10%+ 尺度误差。模糊/拖影让框变大 → \( s \) 变小 → **速度偏低**。NMS 框抖 → 速度抖。

3. **4 FPS + 90px 门控**  
   高速球一帧位移过大 → 重置轨迹 → HUD 突然 0 再跳起来。这是当前「测速时好时坏」的主因之一。

4. **检测目标不是网球**  
   COCO `sports ball` 含足球/篮球/棒球。场边球形物、远距黄线交点、灯光高光都可能进框。HSV 兜底把球场涂装、荧光线当球，**测速应禁用 HSV**。

5. **时间基准**  
   墙钟间隔 ≈ 跳帧后的真实时间，投影速度均值还算自洽；但**峰值瞬时速度**被 250ms 窗口平均掉，发球峰值会严重低估。

6. **自拍镜头**  
   `facingMode: user` 不利于拍球场；手机广角畸变进一步搞坏直径标定。

### 4.4 不换模型也能做的测速补丁（精度仍是「观感级」）

- 用 `video.currentTime` 或给每帧打采集时间戳，禁止用推理结束时间。
- 关联改为「距上一预测位置」而不是距上一框；简单恒速外推，减少重置。
- 最高分改为「距轨迹最近且 score>阈」。
- 框尺寸用中位数 / EMA，禁止单帧直径直接进 \( s \)。
- 连续 N 帧有效才显示速度；miss 时保持预测点但不更新速度。
- 可选：用户点两点标 1m 或底线（README P2），比球直径可靠一个数量级。
- 摄像头默认后置；测速模式强制 ONNX，失败则提示无法估速而不是 HSV。

这些能让 Demo 稳定，**不能**把误差收到「和雷达枪比 ±10%」。要那种精度必须上球场几何 + 高帧率检出（见 5.4）。

## 5. 模型优化与训练方案

检测质量和帧率是测速的上游。速度公式本身几乎没有可训练参数；**精调的是「每帧球心」**，不是回归 km/h。

### 5.1 目标定义（建议拆成两个模型问题）

| ID | 任务 | 输出 | 与测速关系 |
| --- | --- | --- | --- |
| D1 | 单帧网球检测（端侧主路径） | 1 类 bbox + conf | 必须；导出 ONNX 替换 `yolo11n-tennis.onnx` |
| D2 | 短时序定位（可选） | 连续 3 帧 → 热力图球心 | 模糊/不可见帧；端侧重，可先服务端/离线 |
| D3 | 人体 pose | 现有 YOLO11n-pose | 击球分段、手腕门控；可暂不精调 |
| S1 | 速度 | **不训练网络** | 标定 + 跟踪；或日后用球场关键点学单应 |

不建议直接训练「视频 → km/h」：标签要从雷达/Hawk-Eye 来，成本高，且和手机机位域差巨大。

### 5.2 基线与导出

当前基线：`yolo11n.pt`（COCO 80 类）→ ONNX，前端滤 class 32。

推荐替换：

```text
yolo11n.pt (COCO) 
  → 单类 tennis_ball 微调 
  → export onnx imgsz=640（及一份 320 供 ROI）
  → models/yolo11n-tennis.onnx
前端：channels==5（4+1类）走单类解码，不再写死 cls=32
```

训练环境：与现网一致，`conda activate mmpose_gpu` + ultralytics。  
导出约束：`opset=12`、`simplify=True`、`dynamic=False`，与现 `export_tennis_onnx.py` 对齐，保证 ORT Web 1.20.1 可跑。  
另导出 FP16 仅供 WebGPU 开关使用，WASM 回退仍用 FP32。

### 5.3 数据集（精调必须有什么）

按「域」分层，不要只用一种公开赛广播图。

#### A. 公开数据（冷启动，约 2–3 万框量级即可看出 COCO 代理的差距）

| 来源 | 规模与形态 | 用法 | 注意 |
| --- | --- | --- | --- |
| **TrackNet / TrackNetV2 标注** | 广播 1280×720、30fps；约 2 万帧级，点标注 + visibility | 点→正方形框（边长随分辨率，约 8–24px + 10% 边距）；visibility=0 作负样本 | [论文](https://ar5iv.labs.arxiv.org/html/1907.03698)；点标注转 YOLO 框要脚本化，勿手画 |
| **RacketVision 衍生 YOLO 球框** | 约 2 万图、单类球（AAAI 2026 基准衍生） | 主训练集之一，含多拍类，需滤网球子集或当难例 | 许可按原论文 / 平台条款 |
| **Roboflow Universe / Ultralytics Hub 单类 tennis ball** | 从几百到几千张不等 | 补多样机位；**人工抽查**标注质量 | 质量参差，只能当补充 |
| COCO `sports ball` 子集 | 球类混杂 | 作预训练已用；精调时**不要**当正样本，可当难负（足球等） | 避免模型继续把足球当网球 |

TrackNet 类数据的价值：高速、拖影、几乎看不见的球——这正是 COCO 代理最差的区域。

#### B. 本产品域数据（决定手机 Demo 好不好用，**不可省略**）

公开集几乎全是**广播侧向/高位固定机位**。本页是手机手持、自拍/后置、室内灯光、业余场。

建议自建 **TenClip-Ball-Phone**：

| 子集 | 采集 | 标注 | 规模起点 |
| --- | --- | --- | --- |
| 底线对面 / 侧面三脚架 | 1080p 60fps 更佳，至少 30fps | 每帧球框；看不见标 ignore | 20–30 段 × 10–20s |
| 手持跟拍、走动 | 同上 | 同上 | 10 段 |
| 室内黄绿场 + 户外红土/硬地 | 覆盖 HSV 会崩的光照 | 难负：荧光线、广告牌、球框、远处灯 | 各若干段 |
| 多球 / 筐里的球 | 静止球 | 测速时应被跟踪逻辑忽略，但检测仍要认 | 少量 |
| 负样本 | 无人球场、只有人没有球 | 空标注图 | 与正样本 1:1 量级不必，但要有 |

标注格式：YOLO `class x y w h` 归一化，单类 `0: tennis_ball`。工具：CVAT / Label Studio / 先 TrackNet 预标再改。

与人体联动（可选第二阶段）：同一帧存 pose 框，用于「球心须落在扩大后的人/拍 ROI」门控，减少场边误检。

#### C. 测速标定数据（评估 S1，不用于检测损失）

另录 **有参考速度** 的短段，否则无法知道估速改没改好：

- 业余：手机拍 + 消费级雷达枪（或已知发球机出口速度）。
- 无雷达：固定机位俯拍、已知球场线长度，用单应算出的平面速度当伪 GT（仍不是 3D 真值，但可回归几何模块）。
- 记录：视频、机位示意、是否三脚架、参考速度、击球类型（发球/底线/截击）。

这类数据 **不要** 和检测训练集混成「回归球速」的监督，只做评测集。

#### D. 不建议当主数据的

- 纯 HSV 伪标签全自动当 GT（确认偏差会写进模型）。
- 只含特写「手里捏着网球」的图（框巨大，与比赛域相反）。
- 未授权的完整赛事录像商用分发（研究抽帧需自行处理版权）。

### 5.4 训练配方（检测 D1）

数据配比建议（可按实验改）：

```text
Train  ≈  50% 广播/公开（TrackNet 转框 + RacketVision 网球）
        + 40% 手机自建
        + 10% 难负 / 空镜
Val    =  手机域与广播域各一截，分开报 mAP，避免「只在 ATP 镜头好看」
```

Ultralytics 起点（mmpose_gpu）：

```bash
conda activate mmpose_gpu
yolo detect train \
  model=yolo11n.pt \
  data=tennis_ball.yaml \
  imgsz=640 \
  epochs=100 \
  batch=16 \
  mosaic=1.0 close_mosaic=10 \
  hsv_h=0.015 hsv_s=0.7 hsv_v=0.4 \
  degrees=5 mixup=0.1 \
  copy_paste=0.0 \
  scale=0.5 \
  patience=20
```

针对小目标的增强（比默认更重要）：

- 多尺度训练 `imgsz` 在 512–640 抖动；评估固定 640 与 320。
- **不要**过强的大 Mosaic 把球缩到 2px 以下；可对正样本做 copy-paste 小球到空场地图。
- 运动模糊、JPEG 压缩、曝光作为自定义 Albumentations。
- 类别权重 / 忽略 `visibility=0` 的框（只当负区域）。

验收指标（手机 val）：

| 指标 | 冷启动合格 | 测速可用门槛 |
| --- | --- | --- |
| 球 recall @ IoU0.3（小目标用 0.3 比 0.5 诚实） | >0.70 | >0.85 且高速段单独报 |
| 假正 / 帧（空场） | <0.2 | <0.05 |
| 连续命中（轨迹不断开的比例） | — | 底线回合 >80% 帧有球 |

端侧再测：同一 iPhone，ROI+并行后整帧 ms、以及「发球段轨迹是否重置」。

### 5.5 时序模型 D2（可选第二阶段）

YOLO 单帧解决不了「球已成残影」。业界用 TrackNet / WASB：3 帧进、热力图出。

| | 建议 |
| --- | --- |
| 数据 | TrackNet 官方点标注 + 少量手机 3 帧窗 |
| 部署 | 先 **Python 离线** 打轨迹，给测速标定；端侧要再导出很小的热力图网（输入 640×360 量级） |
| 与 YOLO 关系 | YOLO 管「可见且圆」；TrackNet 管「高速残影」。融合：热力峰值与 YOLO 框互相验证 |

浏览器里同时跑 pose + TrackNet 不现实，除非放弃实时、改「录 2 秒再出速度」。产品上可做成：**实时 YOLO 框；停止后用时序模型出一条更准的轨迹和平均速度。**

### 5.6 Pose 要不要精调

挥拍、侧身、球拍遮挡下 COCO pose 会抖。若只做测速，**不是第一优先级**。若做击球瞬间（手腕–球距离骤降），再抽 TenClip 击球片段做关键点微调或蒸馏。与球检测数据可同视频不同标注任务。

### 5.7 量化与蒸馏

顺序：单类 FP32 达标 → 导出 ONNX FP32（对照）→ WebGPU FP16 → 再考虑 INT8（用手机域 200–500 张校准）。INT8 对 6px 球风险高，不要作为测速路径的默认。

蒸馏：教师 `yolo11s` 或 `yolo11m` 单类，学生 `yolo11n`，数据同上。端侧只发 n。

## 6. 推荐实施顺序

```text
1. 测速诚实化：时间戳、关联、禁用 HSV 估速、后置摄像头
2. ROI + 双 run 并行 + 拆分 pose/tennis imgsz   ← 延时主收益
3. 单类网球微调（公开 + 手机自建）替换 COCO 代理
4. 球场线 / 手动 1m 标尺（P2）                 ← 测速主收益
5. 离线 TrackNet 轨迹 + 雷达/发球机评测集
6. （可选）录完再跑时序模型出「回合平均球速」
```

工作量粗估：1–2 为前端一周内可落地；3 含标注是主要工期（自建数据 1–2 周采集标注 + 1–2 天训练导出）；4 是几何不是训练；5–6 才接近「能报一个可引用的数」。
