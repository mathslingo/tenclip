# PRD：姿态关键点（录像后分析）

状态：已定稿，按本文实现  
版本：2026-08-20  
相关：`pose_server_v2.py`、小程序 `pages/pose-live`、`pages/pose-detect`

## 1. 背景

云主机 CPU 跑 RTMPose，单帧 500–800ms。微信小程序再叠加拍照、base64、HTTPS，无法做到跟手实时骨架。

现有「动作分析」上传视频后由 VLM 出**文字建议**。姿态能力应改成**录像 → 离线出骨架回放**，不与动作分析抢同一出口。

## 2. 目标

用户在小程序里录一段短动作，上传到姿态服务，等待分析，观看带骨架的回放。

非目标（本期不做）：实时跟手、端侧模型、VLM 文案、多人追踪 ID。

## 3. 用户流程

1. 打开「姿态关键点」（分析 Tab / 原实时入口）。
2. 预览摄像头，点「开始录制」（最长 8 秒，可提前结束）。
3. 停止后自动上传。
4. 展示「分析中」与进度（已处理帧 / 总帧）。
5. 成功后播放带骨架视频；失败展示原因，可重录。

## 4. 约束

| 项 | 值 |
|---|---|
| 最长录制 | 8 秒 |
| 建议分辨率 | camera `medium` |
| 服务端抽帧 | 6 fps，最多 48 帧 |
| 上传大小 | ≤ 20MB |
| 期望耗时 | CPU 上 8 秒素材约 20–60 秒 |
| 并发 | 单机同时只跑 1 个视频任务 |

## 5. 和小程序其它能力的边界

- **击球剪辑**：长视频抽回合。
- **动作分析**：出中文指导。
- **姿态关键点（本期）**：出骨架回放，不出指导文案。

## 6. API（姿态服务，端口 5000）

生产域名需 Nginx 反代（与 `/health` 同机）。

### `POST /analyze-video`

`multipart/form-data`，字段 `video`。

响应：`{ "task_id": "..." }`，HTTP 202。

### `GET /analyze-video/status?id=`

```json
{
  "task_id": "...",
  "status": "queued|running|succeeded|failed",
  "progress": 0.0,
  "message": "",
  "frame_count": 0,
  "error": null
}
```

### `GET /analyze-video/file?id=`

成功后返回 `video/mp4`（优先 H.264）。

兼容：`POST /detect` 单帧仍保留，不在主入口暴露。

## 7. 小程序

- 主入口改为 `pages/pose-live` 的录制流。
- `pages/pose-detect` 文案改为「录一段动作，生成骨架回放」。
- 分析 Tab 卡片改为同一能力。
- `pose-rtmpose` 实时页保留，不在主路径展示（开发者可直达）。

## 8. 验收

- 真机录 5 秒，能出带回放的骨架视频或明确失败原因。
- `curl` 本机 `/health` 仍为 ok。
- 不改 `tenclip-api`（7861）。
- 本地 SQLite 不入库（任务仅内存 + 临时目录）。
